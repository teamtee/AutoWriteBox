3. 增加真实浏览器工作流测试和调用费用可见性；
4. 完成独立真人连续十章盲读，再决定下一批产品功能。

## 五、P0：发布前必须修复

### P0-1：LLM 上下文预算只覆盖部分调用路径

`buildChapterContextBudget()` 当前主要接入：

- `server/routes/gen.js` 的正文生成；
- 正文生成后的自动审稿；
- `server/chapter-context-manifest.js` 的上下文体检。

以下路径没有统一按实际任务模型的 `modelContextChars` 预算：

- 章节策划的“叙事骨架 → 完整策划”两次调用；
- 全书大纲、核心字段与分部规划；
- 自动 digest 和独立标题；
- 手动审稿；
- 分项修订、审稿精修、候选复审；
- 黄金三章审稿、阶段摘要、记忆重算；
- 新增的核心设定一键填充。

`server/llm.js::validateLlmInput()` 只检查全局 `MAX_LLM_INPUT_CHARS`，没有检查当前模型窗口。因此低于 50 万字符、但高于实际模型窗口的请求仍会被发给上游。

#### 边界复现

用项目允许的合法字段上限组装：

- 手动审稿：525,436 字符；
- 单项修订：511,385 字符；
- 配置 32,000 字符模型窗口、使用完整合法策划卡时，正文生成实际组装 41,899 字符，超出登记窗口 9,899 字符。

这不证明当前作品已经发生故障，但证明预算合同存在结构性缺口。固定 `CHAPTER_PROMPT_FIXED_OVERHEAD_CHARS = 24_000` 也不足以覆盖合法的完整策划卡和动态协议文本。

#### 整改要求

建立唯一 LLM 请求装配入口，统一负责：

- 当前任务最终选择的模型和窗口；
- 动态固定开销计算；
- 分层预算与裁剪说明；
- token/字符保守估算；
- 最终组装后的模型窗口硬校验；
- 输入、输出预算和调用元数据。

所有路由不得绕过该入口直接拼接大型提示词。

### P0-2：审视时的 AI 一键填充会直接、顺序、非原子地写盘

相关文件：

- `web/src/ai-fill-apply.ts`；
- `web/src/components/CoreAiFillBar.tsx`；
- `web/src/components/CharacterCraftCard.tsx`；
- `web/src/components/PromiseLedgerCard.tsx`。

核心循环仍先进入草稿，但人物卡、关系卡和计划承诺会逐条调用保存 API。当前实现没有批量事务和失败回滚；第 N 条失败时，前 N-1 条已经提交。

同时，停止按钮的 `AbortSignal` 只覆盖草稿生成和部分读取请求。进入 `applyCharacterCraftDraft()` 或 `applyPromiseLedgerDraft()` 后，保存回调不接收 signal，循环间也不检查取消状态，因此用户点击停止后剩余条目仍可能继续落盘。

这与“AI 结果先回草稿、人工确认后生效”的产品原则及文档表述不一致。

#### 整改要求

优先采用以下方案：

1. 人物、关系和承诺全部先显示为可编辑候选；
2. 用户逐项核对、删除或修改；
3. 点击一次“应用”；
4. 服务端使用同一修订号进行原子批量提交；
5. 整批成功或整批失败，不允许静默部分成功。

若短期无法实现批量事务，则必须显示逐条成功/失败结果、支持取消检查，并在任何部分失败后强制刷新服务器权威状态。

### P0-3：审视时 AI 计划承诺的起始章下界实现错误

`server/ai-fill-prompts.js` 要求 `expectedStartChapter` 不小于当前规划起点，但 `server/ai-fill-extract.js::extractPromiseLedgerDraft()` 只检查全局 `1..MAX_TOTAL_BOOK_CHAPTERS`，没有执行 `expectedStartChapter >= startChapter`。

当前测试还把该错误行为固化为：`startChapter=4` 时允许模型返回第 2 章。

#### 整改要求

- 起始章至少为 `startChapter`；
- 结束章至少为起始章；
- 起止章均不得超过总章数上限；
- 增加边界、缺失值和超上限测试。

### P0-4：真实阅读价值尚未完成独立验收

《笼中火种》已有连续正文候选和提示词 A/B 记录，但正式真人连续十章盲读仍未完成。现有证据不能证明普通读者愿意连续追读，也不能证明复杂系统相较简单提示词具有稳定净收益。

在该验收完成前，不应继续把更多创作卡片和规则协议视为产品价值已经成立。

#### 整改要求

- 至少一名未参与策划和生成的人连续盲读十章；
- 记录首次犹豫、首次弃读和十分钟后记忆点；
- 只修最早弃读原因，再进行第二轮；
- 建立简单提示词基线，与完整系统对比；
- 覆盖至少两个模型和三类题材。

## 六、P1：下一阶段重点

### P1-1：前端测试没有覆盖真实浏览器交互

前端测试大量使用 `react-dom/server::renderToStaticMarkup` 和纯函数测试，没有 Testing Library、jsdom/happy-dom 交互环境，也没有 Playwright/Cypress。

因此当前测试难以发现：

- 点击停止后的异步行为；
- 页面切换和组件卸载；
- `useEffect` 清理；
- 焦点恢复与键盘操作；
- 双击和快速切章；
- 草稿保护与浏览器离开；
- 批量写入部分成功。

### P1-2：没有模型用量和费用治理

从章节策划到完整后处理，单章最多可能包含叙事骨架、完整策划、正文、digest、独立标题和自动审稿约六次模型调用，后续精修还会继续增加。

当前没有 token/字符使用量、单章费用估算、每日或每书预算、延迟和失败率统计。`server/llm.js` 会忽略兼容服务的 usage 尾帧，请求体也没有 `max_tokens` / `max_completion_tokens`、`temperature` 或 `top_p`。

UI 允许 50,000 字章节目标，但上游模型可能按默认输出上限截断，最终正文被拒绝而费用已经产生。

### P1-3：文档与代码出现行为漂移

已确认示例：

- README 和产品 TODO 说短、漏栏、薄栏的世界/文风圣经不会覆盖旧版；当前代码和测试实际允许落盘，只有格式损坏才拒绝；
- README 说空泛策划不能解锁正文；当前 `server/routes/gen.js` 默认不再阻断不完整策划；
- `server/test/README.md` 说存在 TODO 测试，本次实际 `todo=0`；
- README 部分位置仍称长期记忆候选默认均需人工确认，而当前代码会自动采纳部分 importance=5 候选。

### P1-4：核心文件接近 1500 行硬上限

- `server/store/chapter-workflows.js`：1464 行；
- `web/src/App.tsx`：1394 行；
- `server/routes/books.js`：1073 行；
- `server/store.js`：1162 行；
- `server/prompts.js`：1141 行；
- `server/llm.js`：969 行；
- 多个测试文件为 1498–1499 行。

下一轮相关修改应先拆职责，不应继续贴着硬上限增长。

### P1-5：发布与仓库纪律不足

- 当前直接在 `main` 上保留大量未提交功能；
- `.pi/` 未加入 `.gitignore`，可能误提交代理输入、输出和分析上下文；
- 没有版本 tag、CHANGELOG 和可回滚的正式发布记录；
- 大型提交不利于独立评审、定位回归和交接。

### P1-6：长期记忆自动采纳仍有语义误判风险

`memoryCandidateCanAutoAccept()` 主要依赖 importance=5 且主体、客体都出现在正文中。但主体和客体同时出现并不能证明模型生成的谓词关系成立；否定、假设、谎言、引语和未来计划都可能误入长期事实。

生死、当前位置、物品持有人、能力境界和知识边界等高风险事实不应仅凭字符串共现自动采纳。

- [ ] 模型适配层和结构化输出；
- [ ] 根据真人反馈决定下一批产品功能，而不是继续按协议数量扩展。

## 九、最终判断

当前项目最适合的策略不是继续扩功能，而是：

> 先统一模型调用合同，封住批量写盘风险，建立真实浏览器测试和费用可见性，再用真人连续阅读验证复杂系统是否真的提升追读体验。

工程基础值得保留；接下来的关键是把这些工程能力转化为可验证、可理解、可负担的作者体验。
