# 自动小说盒子 · 章节审稿闭环设计

> 章节写完后，AI 立刻给出可执行的审稿卡：评分、关键问题、修改建议和一键抽打指令。目标是把“生成一章 → 看哪里不行 → 改一版 → 继续写”做成闭环。

- **日期**：2026-08-03
- **范围**：`server/` 章节审稿生成与存储；`web/` 章节审稿卡和一键抽打交互
- **状态**：设计已确认，待用户复审后进入实施规划

---

## 1. 目标与边界

**目标**：

1. 每次章节 `next`、`rewrite`、`whip` 成功后，自动生成一张“章节审稿卡”。
2. 审稿卡必须给出用户能直接行动的信息：综合评分、3-5 条问题、3 条修改建议、3 条可直接用于抽打的指令。
3. 用户点击某条抽打指令后，直接复用现有 `/api/gen/chapter mode=whip`，生成当前章新版。
4. 审稿失败不影响正文保存、digest 保存和章节完成状态。

**边界**：

- 本轮只做章节级闭环，不做全书质量雷达、不做跨章节伏笔追踪、不做版本差异对比。
- 审稿结果是派生建议，不进入章节正文版本链。
- 抽打仍由现有章节版本系统保存新版，审稿卡只负责提供更好的修改入口。

## 2. 用户流程

### 2.1 生成后一眼审稿

章节生成完成后，主区仍显示章节正文，正文下方出现审稿卡：

```text
章节审稿
综合评分：78
一句话判断：冲突成立，但中段推进偏松。

主要问题
1. 争吵升级太快，缺少触发点。
2. 主角反应偏被动，人物锋芒不足。
3. 结尾钩子不够明确。

建议抽打
[强化冲突] [让主角更主动] [结尾加钩子]
```

用户点“强化冲突”后：

1. 对应指令自动作为 `whip` 文本。
2. 前端调用现有 `/api/gen/chapter`，传 `mode: "whip"` 和当前章节 id。
3. 后端已保证 `whip` prompt 带当前章原文，模型能基于原文重写。
4. 新版正文进入 `chapter.body.versions`，用户可用“上一个/下一个”回看。

### 2.2 手动再次审稿

审稿卡提供“重新审稿”按钮。适用场景：

- 用户手动编辑正文并保存后，希望重新评估。
- 上一次审稿失败。
- 用户抽打后想重新看新版质量。

重新审稿只更新审稿卡，不修改正文。

## 3. 审稿数据模型

章节 JSON 新增可选字段：

```json
{
  "review": {
    "score": 78,
    "verdict": "冲突成立，但中段推进偏松。",
    "issues": [
      { "title": "冲突触发点不足", "detail": "争吵升级缺少明确导火索。" }
    ],
    "suggestions": [
      {
        "label": "强化冲突",
        "instruction": "保留现有剧情，把争吵的导火索写清楚，让双方台词更尖锐。"
      }
    ],
    "sourceCursor": 2,
    "updatedAt": "2026-08-03T00:00:00.000Z"
  }
}
```

字段规则：

| 字段 | 规则 |
|---|---|
| `score` | 0-100 整数；无法解析则不写 review |
| `verdict` | 40 字内一句话判断 |
| `issues` | 3-5 条；每条 `title` 15 字内，`detail` 80 字内 |
| `suggestions` | 3 条；`label` 8 字内，`instruction` 可直接传给 `whip` |
| `sourceCursor` | 审稿基于哪个章节正文版本，等于 `chapter.body.cursor` |
| `updatedAt` | 审稿生成时间 |

当用户切到其它正文版本时：

- 若 `review.sourceCursor === chapter.body.cursor`，显示审稿卡。
- 若不相等，显示“审稿对应旧版本”，提供“重新审稿”按钮。

## 4. 后端流程

### 4.1 新增 prompt 与解析

`server/prompts.js` 新增：

```js
buildChapterReviewInstruction({ chapterIndex, content, context })
```

要求模型只返回严格 JSON：

```json
{
  "score": 78,
  "verdict": "一句话判断",
  "issues": [
    { "title": "问题标题", "detail": "具体说明" }
  ],
  "suggestions": [
    { "label": "按钮文案", "instruction": "可直接用于抽打的修改指令" }
  ]
}
```

`server/llm.js` 新增：

```js
extractChapterReview(text)
sanitizeChapterReview(obj)
```

解析规则：

- 先直接 `JSON.parse`，失败则截取首个 `{...}` 再 parse。
- `score` clamp 到 0-100，并转整数。
- `issues` 最多保留 5 条，少于 1 条视为失败。
- `suggestions` 最多保留 3 条，少于 1 条视为失败。
- 文案统一 `trim()` 并截断，避免长文本撑爆 UI。

### 4.2 章节生成后自动审稿

在 `/api/gen/chapter` 中，正文保存和 digest 完成后追加审稿步骤：

1. 读取最新 `book`、`section`、`chapter`。
2. 用 `buildContext({ book, section, prevChapter })` 加当前章正文生成审稿 prompt。
3. 调用 `nonStreamChat` 得到审稿 JSON。
4. 解析成功则写入 `chapter.review`，并 `writeChapter`。
5. 审稿失败只吞掉错误，不改变 SSE 成功结果。

SSE `done` 事件不需要直接携带完整 review；前端继续通过 `reload(bookId, selection)` 获取最新树，和当前模式一致。

### 4.3 手动重新审稿 API

新增非流式接口：

```http
POST /api/books/:bookId/sections/:sid/chapters/:cid/review
```

返回：

```json
{
  "score": 78,
  "verdict": "...",
  "issues": [],
  "suggestions": [],
  "sourceCursor": 2,
  "updatedAt": "..."
}
```

错误：

- 非法 id 或章节不存在：`400 { "error": "..." }`
- LLM/解析失败：`400 { "error": "REVIEW_FAILED" }`

自动审稿失败不打断章节生成；手动重新审稿失败需要 toast 提示。

## 5. 前端交互

### 5.1 新增 `ChapterReviewCard`

只在章节视图显示，位置在 `VersionedBox` 下方、`Actions` 上方。

Props：

```ts
{
  review?: ChapterReview;
  stale: boolean;
  reviewing: boolean;
  onReview: () => void;
  onUseSuggestion: (instruction: string) => void;
}
```

展示规则：

- 有匹配当前版本的 review：显示评分、verdict、问题列表、建议按钮。
- review 过期：显示灰态提示“这张审稿卡对应旧版本”，主按钮为“重新审稿”。
- 没有 review：显示“还没有审稿”，主按钮为“审稿本章”。
- reviewing 中：按钮禁用，显示“正在审稿...”。

### 5.2 一键抽打

点击建议按钮时：

1. 调用 `runChapter("whip", instruction)`。
2. 不再要求用户手动复制到抽打输入框。
3. 生成期间沿用现有 streaming 状态和 Stop 按钮。

原来的手动抽打输入继续保留，作为高级入口。

### 5.3 状态与并发

`App.tsx` 新增：

- `reviewing: boolean`
- `reviewingRef`
- `runExclusiveAction` 包裹手动审稿，防止重复点击。

生成中禁用手动审稿；审稿中禁用建议按钮，避免同时审稿和抽打。

## 8. 非目标

- 不做整本书评分。
- 不做当前版/上一版 diff 审稿。
- 不做审稿历史列表；每章只保留最近一次审稿卡。
- 不把审稿建议写入正文版本历史。
- 不引入新的 LLM provider 配置；复用现有配置。
- 不阻塞章节生成成功链路。
