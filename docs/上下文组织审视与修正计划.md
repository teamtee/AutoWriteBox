# 上下文组织审视与修正计划

本文记录一次针对**上下文组织**的专项审视，以及分阶段的修正计划。审视只覆盖"发给模型的材料如何选择、分配预算和排列"，不涉及存储、并发和 HTTP 合同。

计划本身描述"为什么和做什么"；具体代码放置规则以 [项目架构索引](../ARCHITECTURE.md) 为准，设计原则以 [好看正文：Prompt 与上下文组织](./好看正文-Prompt与上下文组织.md) 为准。

## 实施进度

截至当前工作树，计划中的核心修正已落地：

| 阶段 | 状态 | 结果 |
| --- | --- | --- |
| 0 · 不变量与基线 | 已完成 | 新增全局预算、满配压力和提示词块序测试；四份有界拼接合并为 `prompt-join.js` |
| 1 · 全局预算分配器 | 已完成 | `context-budget.js` 统一分配总额，满配不再硬拒绝；生成与自动审稿共用；全局配置与每个 API 方案模型均可登记 1.6 万—200 万字符窗口；体检显示实际模型预算 |
| 2 · 长程前情 | 已完成 | 当前部／跨部预算调整为 2 万／6 万；单部保留开场、相关、收尾；久远相关部可召回；高置信记忆自动采纳且可否决 |
| 3 · 检索层 | 已完成 | 修复短行套利、单字误命中，增加别名召回和带数量的省略提示 |
| 4 · 提示词排布 | 已完成 | A=事实、B=计划；上一章锚点紧邻策划；当前稿后置；静态清单进入 system；任务句唯一 |
| 5 · 指导语去重 | 已完成并通过真实 API 盲读 | 首轮四篇揭示当前分层组篇幅更足但偶发越过章末；补策划范围护栏后复测 2/2 均停在双入口选择处，平均 4246 字符 |
| 6 · 收尾 | 已完成核心项 | null 交接快照只读降级；上一章正文统一读取权威版本；预算结果进入 API 上下文体检 |

每模型上下文窗口现以 `modelContextChars: Record<model, chars>` 独立保存，不改变旧 `models: string[]` 合同。旧全局配置和旧方案缺失该字段时迁移为 500,000；方案切换、任务模型分工和单书固定模型都会携带对应窗口。无论登记多大，本地仍以 500,000 字符作为输入硬上限。

## 结论

工程质量本身没有问题：分层清晰、有架构门禁、后缀数组检索、修订号锚定长耗时生成。问题集中在**预算与排布策略**——各子系统各自设上限并各自往提示词里塞内容，没有一层负责"这次调用总共只有这么多额度，谁先谁后"。

以下每条都在当前代码和 `data/` 真实数据上验证过，验证方法记录在各节内，便于修正后复算。

## 一、没有全局预算分配器，满配会硬拒绝

`limits.js` 给每个字段独立设了上限，但没有任何一层做总额分配。用满配数据实测装配结果：

```
system 97,746 + context 228,372 + instruction 201,544 = 527,662
> MAX_LLM_INPUT_CHARS (500,000)
→ llm.js:196 validateLlmInput 抛 LLM_INPUT_TOO_LARGE，整次生成失败
```

复算方法：构造 premise/大纲/本部大纲/四项核心设定/三个作用域人物/长期记忆/文风卡全部达到各自上限的书籍，调用 `buildSystemPrompt + buildContext + buildChapterInstruction(mode:'rewrite')`。

`limits.js:44` 的注释写着"以下窗口合计控制在约 26 万字符内"。这笔账已经过期：之后陆续加入的 `MAX_PROMISE_LEDGER_CONTEXT_CHARS`(16k)、`MAX_CHARACTER_CRAFT_CONTEXT_CHARS`(16k)、`MAX_WRITING_ASSET_CONTEXT_CHARS`(16k)、`MAX_MEMORY_CONTEXT_CHARS`(12k)、阶段摘要都没有回过头修正总额，也没有测试守住"各字段上限之和 ≤ 全局上限"这个不变量。

更严重的是失败方式。`ARCHITECTURE.md` 明确写着"门槛应当标注而不是拒绝……拒绝落盘只会让作者白付一次 API 且什么都拿不到"。但上下文超限恰恰是硬拒绝，前端文案是"当前作品上下文过长，无法安全发送给模型；请精简设定或分段生成"。作者写到第 300 章、世界圣经和文风卡都填满时被告知去删自己的设定，且无法判断该删哪一个。

附带问题：`MAX_LLM_INPUT_CHARS` 是写死的 500,000，`llm-config.js` 完全没有 contextWindow 概念。用 32k 上下文的模型和用 1M 上下文的模型拿到同一份预算——前者被服务端静默截断，后者浪费一半可用窗口。

## 二、跨分部前情几乎全丢

`generationPriorSectionSummary` 的实际行为，用 14 部 × 100 章 × 每章 50 字摘要模拟（50 字与本机真实数据的 41–64 字一致）：

```
prior-sections context = 15,047 字符
保留的部：第 11 部、第 12 部、第 13 部    ← 13 个已完成分部里只剩 3 个
第 1–10 部（1000 章）→ 一行"（更早分部剧情已因上下文预算省略）"
```

原因是两级截断叠加：

1. `MAX_BOOK_SECTION_SUMMARY_CHARS = 5,000`，每部只保留尾窗。这个截断在 `store/memory.js` 的 `updateBookSectionSummary` 里、**写入 book.json 时就发生了**，不只是提示词时才裁。
2. `fitRecentBookSummaryRows` 再按 `MAX_BOOK_PROMPT_SUMMARY_CHARS = 20,000` 从最新往回塞，塞不下就整部丢弃。

预算分配本身也失衡：**当前部拿 60,000 字符（够放 1000 章摘要），此前所有部加起来只有 20,000**。当前部实际上已经有"上一章结尾 + 交接快照 + 本部前情"三重覆盖，60k 是浪费；真正会断的是跨部长线，却只给 20k。

设计上的补救是阶段摘要和长期记忆，但两者都需要人工触发。本机 4 本书全部 `memory.facts = 0`、`promiseLedger.entries = 0`、`characterCraft.characters = 0`——其中一本已经写了 14 个分部，一条都没有。这说明补救路径在真实使用中没有跑通，长程连续性实际上完全依赖那个"只剩 3 个部"的尾窗。

## 三、检索层：优先级倒挂与召回缺陷

### 3.1 短行套利导致优先级倒挂

`generation-memory-context.js` 的贪心装填用 `continue` 而不是 `break`，放不下的高优先条目被跳过，后面的低优先短条目继续填充：

```
任务命中 = 1   实际装入的任务命中 = 0   装入总数 = 6
装入内容：['- [other] 路人0｜关系｜站在街', '- [other] 路人1…', '- [other] 路人2…']
```

唯一与本章直接相关的长事实因放不下被跳过，6 条完全无关的短事实把预算填满。文档 §三 承诺的"本次任务直接相关 → 近期上下文相关 → 重要度 → 新近度"在**排序**上成立，在**装填**上被短行套利破坏。

### 3.2 subject 缺长度护栏

`matches()` 里 `fact.object` 和 detail 值都有 `length >= 2 && <= 80` 的护栏，唯独 `fact.subject` 没有。实测单字 subject「火」被正文中的"灯火通明"误命中，占掉高优先级槽位。

### 3.3 别名零召回

检索是精确子串匹配。中文小说里同一人物在正文中是「陆昭 / 昭哥 / 那个瞎子」，别名一换就是 0 召回——而最需要长期记忆的场合，正好就是人物久未登场、称谓已经改变的场合。

### 3.4 省略提示不带数量

`OMITTED_MEMORY_ROW` 只说"其它已确认记忆因上下文预算省略"。`selectedCount / omittedCount / selectedTaskRelevantCount` 都已经算出来了，但只给了作者看的体检面板，没给模型。模型无法区分"省略了 3 条"和"省略了 4 万条"。

### 3.5 三个选择器三种策略

同为窗口选择器：`fitRecentBookSummaryRows` 用 `break`（保尾）、`generationMemorySelection` 用 `continue`（最大填充）、`generationCharacterRows` 用首尾对半。没有统一约定，新增选择器时无从参照。

## 四、排布：声明的优先级与物理顺序相反

实测一次 rewrite 的完整块序（共 24 块）：

```
 1 【上下文分层：…】              ← 声明"越靠前的越优先"
 2 【A. 作品方向与未来计划】        ← 但它自己列的优先级里"计划"是第 2 位
 7 【B. 已发生事实与当前连续性】    ← 优先级第 1 位，却排在 A 后面
14 【上一章结尾】                 ← 最关键的连续性锚点，埋在正中间
17 【当前章原文】                 ← 最多 20 万字符，把 14 和 19 劈成两半
18 重写第 9 章，…                 ← 任务句第一次出现
19 【本章策划卡（作者意图）】       ← 本次任务最具体的指令，在正文之后
22 【硬约束：连续性与知识边界】     ← 声明"最高优先级"，物理位置倒数第三
23 【判断依据：读者为什么会继续读】 ← 789 字通用建议，占据紧邻任务的黄金位
24 请写第 9 章正文，…              ← 任务句第二次出现
```

四个问题：

1. **A/B 编号与优先级相反。** 而且 [好看正文：Prompt 与上下文组织](./好看正文-Prompt与上下文组织.md) §二 定义的是 A=已发生事实、B=作者计划，代码里正好互换了。照文档理解代码的人一定会建错模型。
2. **【当前章原文】把连续性锚点和策划卡劈开。** 20 万字符横在中间，最需要被并置阅读的两块隔得最远。
3. **通用写作建议占了最强的近因位，本章策划卡没有。** 越是"这一章特有"的信息，越应该靠近任务句。
4. **两句任务描述夹着全部指导语**（#18 与 #24），语义重复，且第一句会被后面的内容稀释。

另外 `CHAPTER_EXECUTION_CHECKLIST`（1,085 字符，全书恒定）每次都拼在 user message 尾部。它是完全静态的，放 system prompt 才对——既能被 prefix cache 命中，也不会跟策划卡抢近因位置。

## 五、指导语重复与优先级不唯一

同一条规则在多处以不同措辞出现：

| 规则 | 当前出现位置 |
| --- | --- |
| 章末状态不得静默复位 | `WEB_FICTION_WRITING_PRINCIPLES` 9.1（system）+ `CHAPTER_CONTINUITY_CONSTRAINTS` 1（user）+ `CHAPTER_REVIEW_CRITERIA` |
| 不要密集比喻／排比／同构短句 | principles 3 + `CHAPTER_CRAFT_CONTEXT` 末条 + 审稿标准 + `chapter-prose-metrics` 确定性统计 |
| 世界观展开只推一层 | principles 12 + craft context + 审稿标准 + `world-progress-schema` |
| 伏笔要有载体和当下用途 | principles 11 + craft context + 审稿标准 |

优先级也有四套并存的说法：system 说"严格遵守以下设定"、principles 说"以禁忌约束和用户要求为最高"、`CONTEXT_LAYER_GUIDANCE` 说"事实 > 计划 > 秘密 > 表达"、`CHAPTER_CONTINUITY_CONSTRAINTS` 说"只有下面三条是写错就是错"。四者互不冲突，但要模型自己归并四份排序表。

这与 `ARCHITECTURE.md` 的"context not control"直接相关：**重复本身就在把"创作判断"变回"打勾清单"**。同一件事说三遍，模型会理解成三条硬性要求，而模型为避免违规产出的安全文本，恰好就是读者说的"AI 味"。

## 六、其它

- `chapter-handoff-schema.js` 的 `formatChapterHandoff(null)` 会抛 `BAD_CHAPTER_HANDOFF`。生产路径上 `migrateChapterInPlace` 保证了非 null，但**提示词格式化函数不应该有抛出校验错的能力**——一个数据边角就能让整次生成失败。
- `prompts.js` 用 `prevChapter.content`（派生只读镜像），`chapter-context-manifest.js` 用 `currentText(previousChapter.body)`（权威源）。目前等价，但体检面板的职责恰恰是忠实反映真实发送内容，任一侧改动都会静默失准。
- 预算全部以 UTF-16 code unit 计。中文大致 1 char ≈ 1 token，混排英文／JSON 时偏差很大，而 `chapter-review-revision-prompt.js` 这类会塞 JSON 的路径正是偏差最大的。
- `boundedJoin` 及其 `LLM_INPUT_TOO_LARGE` 判断在 `prompts.js`、`chapter-revision-prompt.js`、`chapter-review-revision-prompt.js`、`golden-three-review-prompt.js` 中有四份近乎相同的实现。

# 修正计划

分 7 个阶段，按"先立护栏 → 再改行为 → 最后调排布"排序。每阶段可独立提交、独立回滚，`npm test` 全绿才进入下一阶段。

## 阶段 0 · 立不变量与基线

目的：后面每一步都能被测试证伪，而不是靠肉眼比对提示词。本阶段不改变任何运行时行为。

| 动作 | 文件 |
| --- | --- |
| 预算不变量测试：所有进入单次调用的字段上限之和 ≤ `MAX_LLM_INPUT_CHARS` | `server/test/context-budget.test.js`（新） |
| 块序快照测试：给定固定输入，断言装配产出的 `【】` 块标题**有序列表**（只断言顺序与存在性，不断言正文内容） | `server/test/prompt-layout.test.js`（新） |
| 满配压力测试：所有子系统填到上限时装配不得抛错 | 同上 |
| 合并四份重复的 `boundedJoin` 到 `server/prompt-join.js` | 新增 + 四处改 import |

阶段 0 结束时满配压力测试是红的（实测 527,662 > 500,000），这正是阶段 1 的验收条件。

## 阶段 1 · 全局预算分配器

对应问题一。

### 1.1 新增 `server/context-budget.js`

```
allocateContextBudget(total, layers) -> Map<id, { chars, trimmed, droppedHint }>
layers: [{ id, priority, floor, want }]
```

分配算法：

1. 先给每层 `floor`；`floor` 之和必须 ≤ `total`，由阶段 0 的不变量测试守住。
2. 剩余额度按 `priority` 从高到低发放到 `want`。
3. 任何层实际额度 < `want` 时返回 `trimmed: true`，由调用方在该块尾部写入**带数量的**省略说明。

层级优先级初版：

| 优先级 | 层 | floor |
| --- | --- | --- |
| 1000 | 硬约束／禁忌约束 | 全量（不可裁） |
| 900 | 本章策划卡 + 场景链 | 全量 |
| 800 | 上一章结尾 + 交接快照 | 2,000 |
| 700 | 当前章原文 | 0（rewrite/whip 时 want=全量） |
| 600 | 已确认长期记忆 | 2,000 |
| 500 | 本部前情 | 4,000 |
| 450 | 跨部前情／阶段摘要 | 4,000 |
| 400 | 本部大纲／全书大纲 | 2,000 |
| 300 | 承诺账本 + 人物导演卡 | 1,000 |
| 200 | 人物名册 | 1,000 |
| 100 | 世界圣经／文风卡 | 2,000 |

### 1.2 接入点

`buildSystemPrompt`、`buildContext`、`buildChapterInstruction` 增加可选 `budget` 参数，由 `routes/gen.js` 在装配前调用分配器。同样接入 `buildChapterReviewInstruction`（它同时携带完整 `context` 与完整正文，溢出风险与生成路径相同）和 `chapter-review-revision-prompt.js`。

### 1.3 预算跟随模型

- `limits.js` 保留 `MAX_LLM_INPUT_CHARS` 作硬上限；新增 `DEFAULT_MODEL_CONTEXT_CHARS`。
- `api-profile-schema.js` 的模型条目增加可选 `contextChars`，`llm-config.js` 透出；未填时用默认值。
- 有效预算 = `min(模型 contextChars × 安全系数, MAX_LLM_INPUT_CHARS)`。

### 1.4 移除硬拒绝

`LLM_INPUT_TOO_LARGE` 保留为最后一道防线（分配器有 bug 时兜底），但正常满配路径不得再触发；`web/src/api.ts` 文案改为诊断向。

**验收**：阶段 0 的满配压力测试转绿；新增测试断言满配时每层都拿到 ≥ floor，且省略说明包含具体数量。

## 阶段 2 · 长程前情

对应问题二。这一步决定百万字长篇能否成立。

### 2.1 配比反转

```
MAX_SECTION_PROMPT_SUMMARY_CHARS   60,000 → 20,000
MAX_BOOK_PROMPT_SUMMARY_CHARS      20,000 → 60,000
```

当前部已经有上一章原文与交接快照的三重覆盖，60k 是浪费；跨部长线才是真正会断的地方。

### 2.2 分部摘要从"尾窗"改为"头 + 关键 + 尾"

`bookSectionSummaryWindow` 当前是纯 `slice(-n)`。改为三段保留：该部开场局面、与本章策划相关性最高的若干章、该部收尾局面，中间标注被省略的章数。相关性复用已有的 `createSubstringLookup`，查询串用 `generationMemoryTaskRelevantText`。

### 2.3 跨部选择不再纯粹保尾

`fitRecentBookSummaryRows` 改为"必留最近 N 部 + 更早部按相关性择优 + 明确标注跳过了哪几部"，让第 3 部埋下的伏笔在第 300 章仍有机会被召回。

### 2.4 记忆自动采纳

零采纳率的根因是人工确认门槛高于收益。

- `store/memory.js`：digest 产出的记忆候选中，`importance ≥ 阈值`且字段完整的默认置为 active，同时标记 `autoAccepted: true`。
- 前端从"逐条批准"改为"列出自动采纳项 + 一键否决"。
- 备份／导入保持兼容：`autoAccepted` 缺省视为 false。

这一步改变默认行为，需单独提交并在 README 说明。

**验收**：新增测试模拟 14 部 × 100 章，断言首部关键条目仍可被召回；断言省略说明包含被跳过的分部编号。

## 阶段 3 · 检索层修正

对应问题三，全部在 `server/generation-memory-context.js`。改动小、收益直接，可与阶段 1、2 并行。

| 问题 | 修正 |
| --- | --- |
| 短行套利导致优先级倒挂 | 分两轮装填：第一轮只装 `taskRelevant`，第二轮才装其余。任务相关项放不下时对该条做字段级截断后仍然装入，而不是整条丢弃 |
| `fact.subject` 缺 `2..80` 护栏 | 补齐与 object／detail 相同的护栏 |
| 别名零召回 | `memory-schema.js` 增加 `aliases: string[]`（上限 8 条 × 40 字）；`matches()` 遍历 subject + aliases；digest 提取时顺带产出别名候选 |
| 省略行不带数量 | 改为"…另有 N 条已确认记忆因预算省略（其中 M 条与本章直接相关）…"，直接复用已算好的计数 |
| 三个选择器三种策略 | 抽出 `fitRowsToBudget(rows, budget, { policy })`，policy 显式声明为 `priority` / `tail` / `head-tail`，三处共用 |

**验收**：把审视中复现的三个 case（优先级倒挂、单字误命中、省略行无数量）直接写成回归测试。

## 阶段 4 · 提示词排布重构

对应问题四。依赖阶段 0 的块序快照测试。

### 4.1 目标块序

```
system:  角色 → 唯一一份优先级声明 → 世界观 → 文风 → 禁忌 → 篇幅
         → 硬约束（连续性与知识边界）      ← 从 user 上移，静态可缓存
         → 判断依据（读者为什么继续读）    ← 从 user 上移

user:    1. 上下文分层说明（缩短）
         2.【事实】此前分部 / 本部前情 / 长期记忆 / 人物
         3.【计划】全书大纲 / 本部大纲 / 世界执行合同
         4.【债务与导演卡】承诺账本 / 人物导演卡 / progress 建议
         5.【上一章结尾 + 交接快照】        ← 上移到紧邻策划卡
         6.【本章策划卡 + 场景链】          ← 本次任务最具体的指令
         7.【当前章原文】（rewrite/whip）   ← 移到策划卡之后
         8. 节奏记录 / 文体趋势 / 体量背景
         9. 任务句（唯一一处）
```

### 4.2 具体改动

- **A/B 互换**：代码里 A=计划、B=事实，文档里 A=事实、B=计划。统一按文档来（文档顺序才符合优先级声明），改代码并同步 `ARCHITECTURE.md`。
- `CHAPTER_EXECUTION_CHECKLIST` 从 user 尾部移入 system。
- `buildChapterInstruction` 的 rewrite/whip 分支去掉开头那句任务描述，只保留末尾一句。
- `CONTEXT_LAYER_GUIDANCE` 中"越靠前的越优先"改为显式编号引用，不再依赖物理位置。

### 4.3 文件拆分

`prompts.js` 现为 1,113 行，`ARCHITECTURE.md` 建议线 800、硬上限 1,500。本阶段会继续增长，同期拆出：

- `server/prompt-guidance.js` — 静态指导语常量（principles／硬约束／判断依据／审稿标准）
- `server/prompt-chapter.js` — 章节生成装配
- `prompts.js` 保留门面与再导出

同时在 `ARCHITECTURE.md`"新代码放置决策"表补两行：预算分配 → `context-budget.js`；静态指导语 → `prompt-guidance.js`。

**验收**：块序快照测试更新为新顺序并转绿；`architecture.test.js` 无新增超线文件。

## 阶段 5 · 指导语去重与优先级归一

对应问题五。

> 冲突时：禁忌硬约束 → 已发生事实 → 本章策划 → 长线大纲 → 表达偏好。信息不足时保留未知，禁止临时补万能设定。
